# DSMM compatibility and upgrade boundaries

**DSMM supports DSH `>=0.2.1-rc.2 <0.2.2-0 || >=0.2.2-rc.1 <0.3.0` and Node.js 22 or later.** Install DSMM into a DSH profile. Its DSH, Cordis, Schemastery and Pi SDK packages are host-provided peers: installing DSMM does not install them into the profile. The CLI's profile resolver supplies modules from the running DSH installation. Optional peer metadata controls package installation; a feature still requires its corresponding host modules when used. Development dependencies remain in the standalone checkout.

After upgrading a profile, let its package manager update the lockfile and restart DSH. An explicitly installed or independently required profile-local DSH package can still shadow the host; review its owner before removing it. Do not force-enable an incompatible provider or change the native HTTP selection to work around a version mismatch.

## Supported integration

Official AgentRegistry, SubagentRuntime and JSONL namespace plugins own execution and storage. Basic role delegation uses native activation results and cancellation. There is no DSMM Registry/Runtime owner to select, manual-runtime overlay to install or persistence companion to configure. Keep the native storage root, compression and unrelated Loader entries unchanged.

Native Web surfaces are Plugins bundle configuration, Settings Profiles, the compact Conversation menu and delegation call views. CLI/headless use native deployment and tools; headless doesn't select Agent presets. TUI and Desktop retain their own carriers and exposed UI capabilities; Web controls aren't necessarily exposed in TUI.

`preset-skills` is internal Agent-scoped installation, not a public Loader plugin. DSMM-managed external LSP defaults to disabled. With the Deepwork module and `lsp.enabled` enabled at startup, it uses the trusted Host install anchor to mount the native MCP client; saving a changed configuration does not remount the running bridge. Native DSH LSP and independently configured MCP remain separate. See [LSP boundary](lsp.md).

### Conversation process summaries

DSH `0.2.1-rc.2` classifies message-level process summaries by tool name: only `subagent` and `subagent_*` enter its subagent category. DSMM delegation tools therefore appear under the generic tools summary even when their individual call cards display the native subagent icon. The separate turn-level delegation classifier has the same name restriction.

The public tool-view slot controls individual call cards, not these summary classifiers. This Host version exposes no dedicated classification contribution or process-group header extension; DSMM retains the native summary behavior. Correct subagent grouping requires a public tool-category contribution consumed by both classifiers, or native recognition of DSMM delegation tools. Recheck in-progress and completed summaries during an authorized DSH upgrade; card appearance alone is not evidence of correct grouping.

## Configuration and actions

Core configuration and native permissions work without a session or active Deepwork. Resolution is defaults → sparse Global → explicit native entry/profile → admitted immutable named overlay. Objects merge, arrays replace, and false/empty/same-default pins remain explicit. Unset only removes the edited layer.

Global and exact native-profile saves are independent. Native form identity/revision and base/user provenance are required; no fallback Global write or cross-layer transaction is implied. Named documents, future-default pointers and actual admission remain separate. Desired saves don't change mounted capability or a running Agent's policy. Without a session, actual admission is unknown.

Save and future-default selection remain available under their own authority. Native **Use profile model** and **Deepwork mode** have independent capabilities. Use profile model consumes the admitted configuration and respects newer native manual model/effort intent, including same-value reselection. With the default `rootModelPolicy: "native"`, root requests retain native assembled selection/defaults; refreshing an admission does not implicitly apply its profile primary or authorize a root fallback channel. Explicit deployment policy `configured` instead gives eligible admitted roots configuration-led primary/fallback routing. It applies equally to Web and TUI roots in that deployment, not by detecting a client; named profiles cannot override the policy. See [model routing](model-routing.md), [Profiles](profiles.md) and [settings/status](settings-status.md).

Stores use separate CAS and atomic-write boundaries. Committed saves aren't rolled back in the response because observation/notification failed: report refresh-required or unsynchronized status. An unconfirmed native mutation requires authoritative reread before retry. Operator, connection and owner lifetime remain valid through precommit; client claims or loopback-looking URLs don't authorize writes.

## Execution and recovery

### DSH 0.2.2 Host differences

DSMM runs identically on 0.2.1 and 0.2.2 Hosts except where 0.2.2 changed public contracts. Runtime capability detection (`agent.model.select` presence, provider-constructor shape) routes each surface; version strings are never consulted.

- **Model selection is fixed before step preparation.** DSMM prepares the selection and request proposal together during admission and maintenance, keeping adapter defaults separate from explicit effort. Configured roots with an explicit primary reassert their admitted selection at public running/inbox boundaries; native roots retain native selection authority. A request that conflicts with its step's fixed provider/model/effort is rejected before dispatch, without scheduling another selection or dropping parameters. A picker change racing a running step can therefore produce a refusal; change models while idle for the next-turn boundary. Plugin metadata associates DSMM-written selections and child setup selections observed between native Session and Agent announcements with their exact events. These remain distinguishable on cold activation without treating setup as new manual intent. The records convey no authority, and same-value selections create no synthetic intent.
- **Cross-route model fallback is unavailable on 0.2.2** (blocked): the request-error contract only allows same-selection retries, so `rate-limit-fallback` route switching degrades to a bounded same-route retry with a one-time diagnostic, and unavailable-route switching refuses outright. 0.2.1 behavior is unchanged. The native `dsh-llm-retry` extension coexists with DSMM's retry ownership.
- **Idle session configuration switching uses current activity.** Completed or stopped roots can select a saved profile or the deployment baseline through native maintenance, including on Hosts without `subagents.list()`. Running resident descendants, observed pending work, queued input and conflicting maintenance still prevent switching. Provider registration alone does not disable the action. Existing children retain their captured configuration; the root's next request and new delegations use the selected configuration.
- **Native tree publication precedes child admission on newer Hosts.** Child requests and tools wait for verified native publication. New delegation requires its exact live creator. Existing members keep the durable creator distinct from the live root that owns admission lifetime. A supported cold member with a complete own restriction ceiling can resume while its creator is absent; native catalog/provider identity, current configuration and captured limits remain required. Legacy records without this evidence retain exact-live-creator recovery.
- **Pending selection is visible at admission.** A DSMM-configured route becomes the client-visible pending model selection as soon as admission completes, and cross-step route changes surface the Host's `[model changed: ...]` notice. This is native 0.2.2 behavior and is not suppressed.
- **fs overwrite observation is restored by the DSMM bundle patch.** 0.2.2 compositions disable `@deepseek-ai/dsh-fs-observation-policy` by default; DSMM's bundle patch re-enables it by id, restoring read-before-write and external-modification rejection (`FS_STALE_VERSION`). The user's profile layer still wins and can explicitly disable it.
- **Adapter capacity defaults changed.** 0.2.2 assumes 1M context / 128K output for models that declare no capacity. Routes served by small endpoints must declare real limits; DSMM's raw seam keeps its explicit-capacity validation.
- **Fake-IP web fetch loses answer-level enforcement.** 0.2.2's HTTP fetch provider neither resolves nor pins addresses (it dispatches through the process-wide proxy policy), so DSMM's Fake-IP adapter cannot validate DNS answers, NAT64-embedded destinations, or answer-level `denyCidrs`. With configured local denies, direct hostnames and native IPv6 literals fail closed where the resolved or translated destination cannot be checked; IPv4 and mapped IPv4 literals retain entry checks. Existing proxy restrictions remain enforced. DSMM never installs a global dispatcher — process transport policy stays Host-owned.
- **pi-ai image-offload bounds are supplied by DSMM** where 0.2.2 requires them (defaults mirroring upstream: `maxRequestImages` 50, `imageOffloadCountQuantum` min(10, max)). 0.2.1 profiles carry no such fields.

### Native history composition

DSMM runs against the unpatched native DSH packages: it installs no Host-side patches and injects no bootstrap flags. Historical support is limited to the existing native reader and validated continuation paths, with no blanket guarantee for historical package versions or additional behavior repair or migration. Native-readable records remain available through history surfaces. Supported persisted DSMM sessions resume with a fresh admission built from the current deployment; persisted mode choices remain user intent, while old delegation authority never survives.

Root and native continuable-child activations load current DSMM prompts/skills/roles and the selected profile ID's latest valid content. Explicit baseline and global-default sources remain distinct. Old immutable revisions and runtime captures are not required for a valid native DSMM descriptor. Missing identity or conflicting/unsafe selection metadata refuses; missing or invalid current named content does not fall back. Parent ownership, catalog/own descriptor, provider, independent composition, readonly/filter/depth and cancellation boundaries are validated before publication. Resident Agents do not hot-switch. Settled one-shot children stay non-resumable.

DSH `0.2.1-rc.2` still checks image capabilities against historical `agent.options` before request routing in affected root model-switch and cold-child flows. Text requests can use a current available route while images fail because the historical model is missing or lacks image support. DSH exposes no public atomic route/options update for that preflight; DSMM leaves the refusal intact and does not modify readonly options or fake capabilities. Resolution requires a public route-aware preflight or supported pre-activation options hook. Recheck both root and child scenarios during each authorized DSH upgrade.

Native continuation replays persisted persona and toolFilter. Current DSMM role tools do not store a persona override, so their role prompt is freshly installed. A historical format embedding a complete DSMM prompt into a native persona registration cannot be replaced through the available DSMM-owned registration interfaces. Such native content/filter restrictions remain effective; an independent historical preset that no longer resolves fails explicitly. A later Host public interface for replacing that owned persona/composition, with native restrictions preserved, is required before claiming that format fully refreshed. Labels or model-produced role text alone never supply missing native/host-owned role identity.

### Execution ownership

Role calls wait for native activation results by default; only `completed` is normal completion. Cancellation after publication uses activation disposal and cleanup. Enabled background execution selects `delivery: 'parent'` before start. The accepted child/message receipt and interrupt acknowledgment aren't completion. Running waiting tasks can't transfer to background.

Queue/Steer retains its native operator and attachment checks. On tree-capable Hosts, model messages preserve the sender and can reach members of the same tree, including supported cold members; interruption requires ancestor authority. Older Hosts retain adjacent-child controls. Listing and interrupt do not wake cold members. A continuation receipt confirms acceptance, not model execution. Missing native capability disables the operation; unknown sends aren't automatically resent. See [Agent presets](agent-presets.md).

Resuming a persisted DSMM session builds a fresh admission and validates its mounted composition. Native membership and current policy provide authority; own PluginRecords supply only profile selection and restrictive ceilings. The current profile cannot expand a member's captured readonly, tool, delegation-target or DSMM depth limits, including through newly delegated descendants. Generic native members retain their native model and null role/level. Without creator residency, a complete own ceiling and verified current native root are required. Readable history remains available; no persona substitution, session reset or automatic import is performed. Native factory load/repair can precede the created guard, so a refusal doesn't promise the log was never opened. Clear/compact can retain policy only with the exact live object and admission, not inferred lineage.

Standard supported model calls use native prepared calls. Raw/custom and Pi-AI stop-only calls use the minimal public completions seam for self-contained literal or explicit model-mapping configurations. Catalog-backed raw combinations that can't be reliably reproduced are rejected for both native and DSMM parameter sources, without disabling standard Coding. Native effort encoding/capability metadata isn't rewritten. See [model routing](model-routing.md).

## Retired compatibility surfaces

No old SDK branch, legacy-read host, cold-profile migration, session repair or custom-owner selector is a 0.3.17 activation path. Old libraries, captures and unmarked history aren't copied, rewritten, repaired or adopted by same-name fallback. Retired brand calibration/default-effort and MaxReasoningPresets fields reject with `deprecated-field`; edit configuration deliberately using generic routes and parameters.

Published **0.3.0 retains its rc.1 identity**, immutable tag, package, assets and version-bound receipt grammar. Historical release controls interpret those records under their original identity, not as a runtime compatibility branch.

## Installation boundaries

Evaluate an authorized built artifact in an isolated home/profile as in the [README](../README.md#use-a-local-artifact). Real Desktop/TUI/CLI plugin installation needs exact authorization and a DSH Host satisfying `>=0.2.1-rc.2 <0.3.0`; it doesn't authorize upgrading the Host, touching credentials/history or copying a Desktop profile into another carrier.

Desktop plugin installation follows publication and uses the Desktop-owned carrier within that Host range; it doesn't authorize a Host upgrade. [Release controls](releasing.md) define publication and delivery. [Fake-IP fetch](web-fetch-fakeip.md) owns network details and limits; shell rejection remains unresolved. [Native permissions](native-permissions.md) defines approval scope.
